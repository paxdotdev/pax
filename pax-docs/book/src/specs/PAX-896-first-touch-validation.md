# PAX-896 First-Touch Validation

Authoring Date: 2026-04-30

## Scope

Validate the non-workspace, third-party flow for a new Pax project generated by `pax-cli`.

The generated project should stay publish-channel clean. Redo can use local source overrides while it is developed alongside Pax core, but those overrides should not be emitted by `pax-cli create` for normal userland projects.

## Current Result

`pax-cli create` now produces a clean project without `[patch.crates-io]` entries and includes:

- `AGENTS.md`
- `CLAUDE.md -> AGENTS.md`
- first-touch docs guidance using real `pax-cli docs` commands

The generated project still cannot build from published crates today.

Command:

```sh
rm -rf /tmp/pax-896-third-party-hello
target/debug/pax-cli create /tmp/pax-896-third-party-hello --libdev-mode=false
cd /tmp/pax-896-third-party-hello
/Users/zack/code/pax/target/debug/pax-cli build --target web
```

Failure:

```text
failed to select a version for `pax-kit`
versions that meet the requirements `^0.38.3` are: 0.38.3

package `pax-896-third-party-hello` depends on `pax-kit` with feature `designtime` but `pax-kit` does not have that feature.
```

The improved parser-build fallback now reports this as a parser build failure that may be caused by syntax errors, dependency feature mismatches, or missing local path patches.

As a deeper check, a throwaway manifest was manually adjusted to avoid the first feature-resolution error by changing `designtime` to forward to the published `pax-kit/designer` feature and by removing the generated `webgl` feature. That got past `cargo metadata` and static analysis, but the web build still failed during `#[pax]` macro expansion with missing or changed runtime/manifest symbols such as:

- `pax_engine::pax_language`
- `pax_runtime::PropertyScopeDescriptor`
- `pax_runtime::ComponentDescriptor`
- `ComponentTemplate::from_parts`
- `TemplateNodeDefinition::selector_info`
- `ComponentDefinition::timelines`

This points to a broader publish-channel skew, not only a stale template feature list.

## Pain Points

- The public template path and published `pax-kit 0.38.3` metadata are out of sync. The generated `Cargo.toml` exposes project features like `designtime`, `designer`, `parser`, `web`, `webgl`, `macos`, and `ios` by forwarding to `pax-kit` features; published `pax-kit 0.38.3` does not expose at least `designtime`.
- After manually bypassing that metadata issue, the published 0.38.3 crates still appear out of sync with the macro-generated code expected by the current CLI/template flow.
- The failure appears during `cargo metadata`, before normal build diagnostics or Pax syntax diagnostics can help.
- Without a release or explicit local override, a fresh userland project cannot reach hello-world web build viability.

## Recommendations

- Do not add generated `[patch.crates-io]` entries or a public `--pax-kit-path` escape hatch to normal userland projects. Keep local source linking in Redo or other intentional validation fixtures.
- Fix the publish-channel contract before declaring first-touch viability. The likely clean path is a coherent Pax release where `pax-cli`, template `Cargo.toml`, `pax-kit`, `pax-macro`, `pax-engine`, `pax-runtime`, and `pax-manifest` agree on features and generated-code APIs.
- Do not land a template-only workaround for the `designtime` feature mismatch unless it also proves a full hello-world web build against published crates.
- Add CI that runs `pax-cli create --libdev-mode=false` outside the Pax workspace, then runs `cargo metadata` and a web build using publish-channel dependencies.
