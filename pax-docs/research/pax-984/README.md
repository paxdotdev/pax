# PAX-984 - Scope the static blog

22 September 2026, hosting decision updated 24 September. Original research followed by an authorized foundation implementation. **Zola/Tabi at `/blog` and Cargo `server_owned_prefixes` are now selected; production deployment and final content remain pending.** The selected hosting plan reuses `s3://www.pax.dev/blog/` and defers Terraform. See [the implemented blog project](../../../pax-blog/README.md) and [hosting coordination notes](../../../pax-blog/infra/README.md).

Initial review copy: [Linear research document](https://linear.app/paxdev/document/pax-984-static-blog-recommendation-and-evidence-22-september-e617094ca5a5). This local note also includes the subsequent URL/routing discussion; those additions have not been mirrored to that document. The original fixture preview is retired; use `python3 pax-blog/blog.py serve` for the implemented project. The current deployment handoff is recorded on PAX-869.

Recommend **Zola 0.23.6 with a small Pax overlay on Tabi 5.0.0**, published as static files at **`https://www.pax.dev/blog/`**, provided the host and Pax navigation share an explicit boundary for document paths. The follow-up discussion makes this the preferred proposal; `blog.pax.dev` remains the option with greater deployment independence. Use semantic HTML for articles and navigation, and optional, isolated Pax applications for interactive illustrations. Keep Substack for newsletter delivery. Publish the approved PAX-978 changelog as the first new post; import history as a distinct second phase before closing PAX-984.

This best matches the Rust preference while keeping publishing maintenance small. Hugo is the strong alternative if a permissive generator license or a larger theme ecosystem takes priority. Cobalt is viable, but offers a less developed theme starting point. mdBook remains the right tool for Pax's book-shaped documentation; adapting its content model into a blog would create avoidable custom infrastructure.

The selected foundation is **Zola/Tabi + `/blog` with `server_owned_prefixes` in Cargo web metadata**. Zack authorized implementation, a monorepo `pax-blog/` project, an announcement stub, local validation, and an undeployed Terraform draft. Final content, archive migration, embedded demos, and publication remain separate work. Google states that it has no indexing or ranking preference between subdirectories and subdomains in its [crawling and indexing FAQ](https://developers.google.com/search/help/crawling-index-faq). The case for `/blog` here is a coherent product/content site, not an automatic ranking improvement.

### Why restyling mdBook is not enough

The [Rust source README](https://github.com/rust-lang/rust/blob/main/src/tools/rustbook/README.md) identifies rustbook as a wrapper that trims optional mdBook dependencies and integrates Rust's custom preprocessors/build. The repo actually invokes `mdbook`, not `rustbook`. Unless Zack meant a different project, this is the relevant identity.

Hiding the sidebar only changes presentation. We would still need a post registry, front-matter ingestion, dated sorting, taxonomies, author metadata, pagination, feed/sitemap generation, and per-post SEO fields. Those can be implemented through preprocessors or a renderer, but then Pax owns a small publishing engine and its integration with mdBook upgrades. The book's stable chapter hierarchy, next/previous chapter model, global description, and Rust-code tooling are excellent for docs; they do not replace blog collections. Keep the current docs pipeline independent.

### Build and operational burden

Zola and Cobalt can be installed as prebuilt binaries; source builds need Rust/Cargo. mdBook likewise has prebuilt binaries; 0.5.4 source requires Rust 1.88. Hugo has prebuilt binaries; Go is needed for source builds or some module workflows. A theme may additionally require Sass/Node tooling; choose a vendored, pinned theme that builds without npm. Tabi 5.0.0 builds here using Zola alone, including Sass and Rust highlighting. Pax example compilation is a separate Rust/wasm-pack job, with Node/NVM needed only when rebuilding the monorepo web interface.

All four leave static HTML/CSS/JS/assets to host. None needs to run its preview server in production. Ongoing work is dependency updates, content review, link/media checks, and controlled static publication. Cobalt and mdBook would leave more blog-specific code to maintain. Hugo is competitive operationally; Rust preference and Zola's sufficient built-ins decide this recommendation.

## Theme and reading direction

Use [Tabi 5.0.0](https://github.com/welpo/tabi/tree/v5.0.0), **MIT**, as the initial reading system. Its [theme manifest](https://github.com/welpo/tabi/blob/v5.0.0/theme.toml) requires Zola **0.23.6**. It provides article/archive/tag layouts, optional JavaScript, and documented extension points. [PaperMod](https://github.com/adityatelange/hugo-PaperMod) (MIT) is the Hugo comparison point. Neither a theme's accessibility claims nor Lighthouse badge certifies our branded site.

Visual direction: the current website's warm black `#11110F`, paper `#FCF9F2`, gray `#B3B3B3`, and signal yellow `#F2F32B`; Manrope headings/body with IBM Plex Mono labels/code, locally hosted after checking font assets/licenses. Keep the article measure around 65–75 characters, body at 18–20px desktop, comfortable mobile padding, fine dividing rules, square-edged surfaces, and underlined article links. Reserve saturated color and motion for actions and optional demonstrations.

Wireframe: compact Pax / Notes masthead → article title → author, original date, tags → optional wide illustration → readable single-column article → related posts / archive → newsletter and get-started links. Index: one featured newest post, then dated rows, archive/tags/feed links. Small screens keep the same reading order and stack navigation; avoid an always-open documentation sidebar. Keep skip links, keyboard focus, selectable text, table overflow, useful image alternatives, print styles, and reduced-motion behavior.

The [local fixture](fixture/) demonstrates a light overlay on Tabi, not the final design or release article. Site-local `templates/tabi/extend_head.html` works without editing the theme. The spike discovered that Tabi emits `og:url` but no self-canonical by default; the override adds one while respecting explicit canonical overrides. Custom CSS needs sufficient specificity to override Tabi's OS-dark selectors. Use the documented head/body extension points for the optional embed loader; override only necessary header/footer files. Disable comments, analytics, search, and extra scripts unless their value is established.

## URL and static hosting proposal

Public HTTP inspection on 22 September: `pax.dev` redirects to `https://www.pax.dev/`; the final response advertises AmazonS3 and CloudFront. `www.pax.dev/blog`, `/blog/`, and a missing nested blog path return 403. `blog.pax.dev` did not resolve. These observations do not reveal private distribution policies. A subsequent read using the supplied `pax` profile succeeded. `www.pax.dev` uses distribution `EYKZZ3KH242XU` with one S3 website origin and no path behaviors, functions, or CloudFront custom errors; its website bucket has an `index.html` suffix and no error document. See the deployment notes for the verified snapshot and proposed addition.

| Concern | `blog.pax.dev` | `www.pax.dev/blog` — preferred after discussion |
| --- | --- | --- |
| Origin/CDN | Separate static bucket/origin + CloudFront hostname/certificate/DNS; isolated rollout and rollback | Blog origin selected by `/blog` and `/blog/*` behaviors on website distribution, or carefully composed static output |
| Base URL | Zola `base_url = "https://blog.pax.dev"`; `/pax-0-39-0/`, `/atom.xml`, `/sitemap.xml` | `base_url = "https://www.pax.dev/blog"`; assets/links include `/blog`; physical output remains relative to blog root |
| Pax navigation | Cross-origin `Link target=Current` takes ordinary document navigation | Implemented `server_owned_prefixes` delegates these links to browser navigation; production still needs the CDN behaviors |
| Failure/caching isolation | Blog 404s, invalidation, deployment credentials and policies separate from main site | Main-site SPA/error fallback and deploy deletion rules must exclude blog; distribution-wide custom errors need particular care |
| Branding/canonical | Shared visual identity and ordinary cross-site links; one canonical host | Unified path; one canonical URL per article, correct root robots/sitemap references require site coordination |

The pre-implementation same-origin navigation issue was concrete: `pax-compiler/files/interfaces/web/src/classes/native-element-pool.ts`, `navigate()`, pushes route history for every same-origin `current` target and returns before `window.open`. Even an absolute `https://www.pax.dev/blog/...` URL is same-origin on the deployed website. CDN routing cannot see this client-only navigation. A central path policy should send `/blog` and descendants through ordinary current-tab document navigation, covering both `Link` and `NodeContext::navigate_to`, with segment boundaries so `/blogger` does not match and query/fragment preservation. The agreed setting is `[package.metadata.pax.web].server_owned_prefixes`; the implementation includes canonical docs, API comments, tests, and removal of the website placeholder route.

### Existing support and the initialization boundary

The related implemented feature is the project's **`public/` directory**, introduced in commit `7b7f160be`, rather than an HTML-serving Router node or Cargo route field. [Web public files](../../book/src/targets-build-deploy.md#web-public-files) documents it. `pax-compiler/src/building/web_public.rs` copies those files into the web build; `pax-compiler/src/building/web.rs` applies that path for builds. The development server in `pax-compiler/src/design_server/mod.rs` serves generated files, then public files, before its history fallback. Existing tests cover public HTML and directory indexes; they were inspected, not rerun in this research follow-up. The website already has `public/ai/index.html` and `public/ai.md`.

Consequently, a generated `public/blog/post/index.html` can contain the complete article and load without Pax. It still needs normal directory-index handling in production. The existing `/blog/*` placeholder declares route metadata and can generate `blog/index.html`; that placeholder must stop owning the static blog path before composing output, because public files deliberately cannot overwrite generated route entries. A separate blog origin avoids packaging the outputs together but still requires the application to yield navigation to that path.

`RouteMetadata` and `[package.metadata.pax.web]` are a separate existing feature: they generate document-head metadata and application entry HTML. They do not turn a Pax screen into static article HTML. That initial inspection found no exclusion policy. The implementation now adds `server_owned_prefixes` to the existing Cargo web namespace and emits it into the application entry HTML plus server-readable `pax-web-config.json`. It also excludes missing server-owned paths from local application fallback.

The two entry cases should converge on the same HTTP handling:

| Entry | Proposed flow | Pax initialization required for the article? |
| --- | --- | --- |
| Direct link or reload | Browser requests `/blog/post/`; CloudFront serves blog HTML | No |
| Link in the running Pax app | Chassis recognizes a document path and performs browser navigation; CloudFront serves the same blog HTML | No additional Pax startup; the app was already running |

CloudFront supports [path-based cache behaviors with origin selection](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesCacheBehavior.html). Configure `/blog` and `/blog/*` before the default behavior and, where needed, use a [viewer-request directory-index rewrite](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/example_cloudfront_functions_url_rewrite_single_page_apps_section.html). This does not require an nginx service or a client redirect through a Pax entry page. Keep blog missing-page responses out of the app's history fallback. A fresh article request should return substantive HTML without requesting the root application's JS/Wasm; optional article demos load separately on activation. Navigating from the app to the article unloads the app document, so returning to Pax may require initialization again unless the browser restores it from its back/forward cache.

For either option, use static S3 + CDN, not a new reverse-proxy process. Resolve directory URLs to their own `index.html`, and return a real not-found response for missing posts/assets. CloudFront's [default root object does not automatically resolve subdirectories](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DefaultRootObject.html). With a private S3 REST origin, configure a narrow directory-index rewrite. For `/blog`, match the behavior before rewriting and either store the complete output under `blog/` or strip exactly one `/blog` prefix; do not accidentally add it twice. A [URI rewrite does not change the selected behavior/origin](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-function-restrictions-all.html).

Use absolute generated permalinks for canonical/social/feed URLs and generator URL helpers for assets. Redirect `/blog` to `/blog/` where appropriate; if choosing a subdomain, later make the main site's blog navigation point there and retain a deliberate `/blog` entry redirect. Do not expose both variants as separately indexable articles. Verify direct loads, refresh, anchors, back/forward, missing pages, escaped paths, and all assets on the deployed preview.

HTML, feeds and sitemap: short shared-cache lifetime or revalidation, cache minimum TTL zero where needed. Fingerprinted assets and content-addressed Pax bundle directories: long immutable caching. Current Tabi uses query hashes for CSS; either include those queries in the cache key or use hashed filenames before claiming immutable asset safety. Serve correct MIME types (`text/html`, CSS/JS types, `application/wasm`, Atom/RSS XML), gzip/Brotli as supported, and keep matching JS/Wasm files together. [CloudFront relies on origin MIME metadata](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/AddRemoveReplaceObjects.html). Upload new assets before HTML/feeds; invalidate mutable paths; retain prior bundles for old cached pages and rollback.

## Pax embedding: checked contract and remaining proof

**Use a same-origin iframe per compiled Pax application.** An iframe is a template slot for real Pax content; the article itself remains static HTML. This is supported by the repo's existing docs-host pattern and avoids pretending the current web runtime is a multi-instance DOM widget SDK.

Evidence at this worktree's HEAD:

- `pax-compiler/files/interfaces/web/src/index.ts`: `mount(selector_or_element, extensionlessUrl)` has module-global chassis/state and rejects a second mount. It loads sibling `pax-interface-web.css`, imports `<cartridge>.js`, fetches `<cartridge>_bg.wasm`, then initializes the chassis. `setSuspended(bool)` is exported and can be called before Wasm initialization finishes.
- `src/styles/pax-web.css` targets `html`, `body`, `#mount`, canvases and global text elements. `src/events/listeners.ts` attaches window listeners; native-pool navigation, scrolling and image loading use the document/window. Mounting directly into an article would require a genuine isolation/lifecycle audit, not a CSS patch. Shadow DOM alone does not fix these assumptions.
- `public/index.html` handles `?pax_route=` by setting a base URL beside the physical entry document. The docs' `pax-docs/book/theme/pax-examples.js` uses `pax_route=/` and `pax_suspended=1`, with a same-origin frame, IntersectionObserver and document visibility. `targets-build-deploy.md` documents the suspension behavior, including wall-clock catch-up.

Proposed authoring: a short template component/shortcode such as `pax_example(id="living-quilt", title="Living Quilt")` looks up an allowlisted bundle manifest. Build that app with the chosen pinned Pax revision and `pax-cli build --target web --release`; place the **entire** output under `_pax/<id>/<content-hash>/`, including interface JS/CSS, cartridge JS/Wasm, snippets, assets, and public files. Reference `_pax/<id>/<hash>/index.html?pax_route=/&pax_suspended=1` through Zola's base-aware URL helper. Do not hardcode `/assets` or rely on a production canonical URL to locate the bundle.

Render a poster, caption, descriptive standalone link, and an explicit **Run example** control in HTML. Load the iframe only on activation; keep the caption/link usable if JS, Wasm, fonts or GPU initialization fails. Give the frame a title and responsive reserved dimensions. Same-origin hosting lets the parent call `frame.contentWindow.Pax.setSuspended(...)` after load; suspend when offscreen/hidden and honor reduced motion with activation rather than autoplay. Multiple examples get distinct browsing contexts. Restart replaces the iframe; suspension retains state and is not general cancellation of application effects or timers.

Tabi's current CSP allows external video frames but not same-origin Pax frames by default; explicitly allow `frame-src 'self'` for the embed. Configure the child response's own CSP/inline bootstrap/Wasm permissions from its actual generated output, including any external fonts. An iframe with `allow-scripts allow-same-origin` isolates styles/state but is **not a security boundary for untrusted same-origin code**; use only reviewed Pax bundles. Cross-origin demos would need an explicit message protocol for suspension; the existing direct-window API would not work.

Remaining bounded proof after alignment: one real release embed at a nested path, then two simultaneous frames; check asset/font/snippet requests, GPU/CPU behavior, interaction, wheel/touch propagation, keyboard entry/exit, responsive sizing, suspension/restart, failure fallback and no-script reading. No fresh Pax runtime build or browser execution of an embed was performed in this research pass. Direct in-page multi-mount support is not claimed.
